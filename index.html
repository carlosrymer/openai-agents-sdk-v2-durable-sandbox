Does splitting the harness from compute actually buy you anything?

The OpenAI Agents SDK v2 makes two falsifiable promises about separating the agent harness (control plane) from the sandbox (compute plane): credentials stay out of the execution environment, and a run survives losing that environment. I tested both against real containers, a real credential-theft probe, and a real process kill.

Claim 1 — Credential isolation

API keys and host credentials do not reach the environment where model-generated code runs.

Claim 2 — Durable execution

Snapshot + rehydration let an interrupted agent resume instead of restarting from zero.

How this was tested

Both experiments run the SDK's real sandbox stack. The only substitution is the model: this environment has no OpenAI API key, so the agent loop is driven by a third-party model through the SDK's LiteLLM integration. That substitution is valid here because the sandbox shell tool is an ordinary FunctionTool — nothing in the harness/compute boundary depends on which model is talking.

Two models appear below, which needs explaining rather than hiding. The durability run (experiment 2) used Gemini 3.6 Flash; those API credits were exhausted partway through this build, so the agent-driven pass of experiment 1 used Kimi K2.7 Code via Moonshot's OpenAI-compatible endpoint. Neither measurement depends on the model — the exfiltration probe is a fixed script and the snapshot/restore path is non-model code — but I would rather say so than quietly present one model.

Every number on this page is read from committed JSON artifacts produced by the runs in experiments/. Nothing is computed in the browser.

Claim 1 — Credential isolation

One byte-identical exfiltration probe, two sandbox providers that ship in the same SDK release. The probe enumerates the environment, reads credential files and /proc/1/environ, checks whether the harness source tree is visible, and then tries to use anything it finds by making a real authenticated API call. The naive side is not a strawman I built — it is the SDK's own unix_local provider.

Why the two providers differ

This is not a configuration accident — it is two different lines of library code. The Docker provider builds the container environment from the manifest alone; the unix_local provider starts from a copy of the host environment. 

# agents/sandbox/sandboxes/docker.py  — container env is manifest-only
environment: dict[str, str] | None = None
if manifest:
    environment = await manifest.environment.resolve()
create_kwargs = {..., "environment": environment}

# agents/sandbox/sandboxes/unix_local.py — host env copied, manifest layered on top
env = os.environ.copy()
env.update(await self.state.manifest.environment.resolve())

There is no manifest option to pass the host environment through to a Docker sandbox. Isolation is structural there. It is equally structural — in the opposite direction — under unix_local.

Agent-driven probe (the model looking for credentials itself)

A realism check on the fixed probe: the model hunts for credentials itself via the shell tool. It reaches the same conclusion on both providers. Worth noting that on docker the model reported GPG_KEY as a credential — it is the base image's public Python-release verification key, not a secret. That false positive is exactly why the deterministic probe, which matches recovered values against the harness's own secret fingerprints, is the primary measurement here.

Claim 2 — Durable execution

A deliberately harsh test, repeated across several trials. The agent builds a Roman-numeral library over six turns — converter, inverse, input validation, then a working CLI — so there is real accumulated state to lose. Halfway through, both planes die: the harness process exits, and the container is destroyed with docker rm -f. A brand-new OS process then loads the serialized session state from disk and rehydrates.

Library-side vs OpenAI-hosted

The crux of this build: how much of the sandbox story actually needs OpenAI's API? I expected the interesting parts to be hosted. Almost none of them are.

Caveats and what I did not test

  • Snapshotting is opt-in and manual. The default is NoopSnapshot, and session.stop() is the only thing that writes one. There is no automatic or periodic checkpointing, so any work done after the last explicit checkpoint is lost. Every trial checkpointed at a turn boundary, which flatters the result.
  • Isolation is about credentials, not the network. The Docker sandbox still had full outbound internet access. It simply had nothing to authenticate with. A sandbox that can reach the internet can still exfiltrate whatever is inside the workspace.
  • The apply_patch tool was not exercised. It is a model-native CustomTool, so the Codex-style filesystem editing path needs an OpenAI model. My agent used shell heredocs instead. This is the one advertised sandbox capability I could not reach without a key.
  • Sandbox memory was not exercised — it defaults to OpenAI models for its two extraction phases.
  • Hosted sandbox providers were not tested. Blaxel, Cloudflare, Daytona, E2B, Modal, Runloop and Vercel all need vendor keys I do not have. Whether they behave like the Docker provider or like unix_local is unverified — the point of Claim 1's result is precisely that this varies by provider.
  • Small run, and two different models. Six agent turns on one task, four trials. The durability trials ran on Gemini 3.6 Flash; the agent-driven probe ran on Kimi K2.7 Code after Gemini credits were exhausted mid-build. This measures the SDK's plumbing, not model quality, and it is far too small to say anything about the latter.
  • The kill always lands at the same point. Every trial destroys the container at a clean turn boundary after turn 3. I did not test killing mid-tool-call, mid-write, or during the snapshot itself — which is exactly where durability gets hard.
  • The agent-driven probe produced a false positive. On docker the model reported GPG_KEY as a reachable credential; it is the base image's public Python-release verification key. That is why the deterministic probe, which matches recovered values against the harness's own secret fingerprints, is the primary measurement rather than the model's opinion.
  • ~/.aws/credentials did not leak even under unix_local, because that provider rewrites HOME to the workspace root. I had expected it to leak, and it did not — reported here rather than quietly dropped.
